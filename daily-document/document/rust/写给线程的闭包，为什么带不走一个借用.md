# 写给线程的闭包，为什么带不走一个借用

你大概遇到过这样的报错：一个在 main 函数里用得好好的闭包，塞进 std::thread::spawn 之后，编译器立刻翻脸，说 borrowed value does not live long enough，或者 closure may outlive the current function。错误里还会冒出 'static 和 move 这两个词。这不是编译器在无理取闹——它是在提醒你一件很容易被忽略的事：新线程可能在你这个函数返回之后还活着，而它带走的每一个引用，都必须真的能活到那一刻。

## 一次典型的编译失败

先看一个最小复现。这段代码看起来天经地义：

```rust
use std::thread;

fn main() {
    let name = String::from("Rust");

    let handle = thread::spawn(|| {
        println!("hello, {}", name); // 这里借用了 name
    });

    handle.join().unwrap();
}
```

编译它会得到：

```
error[E0373]: closure may outlive the current function, but it borrows `name`,
which is owned by the current function
  --> src/main.rs:6:32
   |
6  |     let handle = thread::spawn(|| {
   |                                ^^^ may outlive borrowed value `name`
7  |         println!("hello, {}", name);
   |                                   ---- `name` is borrowed here
```

注意报错说的是"闭包可能活得比当前函数久"。这里的关键是"可能"——即使我们紧接着就 join 了，编译器也不会因此网开一面。原因下面会讲。

## 编译器在担心什么

thread::spawn 的签名大致是这样：

```rust
pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T,
    F: Send + 'static,
    T: Send + 'static,
```

看到 F: 'static 了吗？这个约束在说：传给线程的闭包，不能持有任何"活不够久"的引用。

为什么非要 'static？因为线程和启动它的函数是**解耦**的。spawn 返回之后，你可以把 JoinHandle 存起来，甚至传到别的函数里；你可以在中途 return，让线程继续跑。编译器不会去分析你"实际上"有没有 join——它只看类型。如果允许一个借用局部变量 `&name` 的闭包逃脱当前函数，那么函数一返回，name 就被销毁，而线程可能还在打印它，这就是一个 use-after-free。

所以 'static 在这里的真实含义不是"这个闭包要永远活着"，而是"这个闭包不依赖任何会在当前函数结束前失效的东西"。一个不捕获任何引用的闭包，或者只捕获了拥有所有权的值（比如把 String move 进去），天然满足这个条件。

## move 关键字做了什么

最常见的修法是给闭包加上 move：

```rust
use std::thread;

fn main() {
    let name = String::from("Rust");

    let handle = thread::spawn(move || {  // 加上 move
        println!("hello, {}", name);
    });

    handle.join().unwrap();
}
```

move 会强制闭包把用到的变量**按值捕获**。原来的闭包里 name 是一个借用（类型是 &String），加上 move 之后，闭包自己拥有了这个 String。既然值归闭包所有，它的生命周期就跟着闭包走，不再依赖 main 的栈帧，'static 约束自然满足。

这里有个容易混淆的点：move 并不改变 String 本身的行为，它只是改变了**捕获方式**。对 Copy 类型（比如 i32）来说，move 就是复制一份；对非 Copy 类型来说，是把所有权转进闭包。转移之后，main 里就不能再用 name 了：

```rust
let handle = thread::spawn(move || {
    println!("hello, {}", name);
});

// println!("{}", name); // 编译错误：name 已经被移动进闭包
handle.join().unwrap();
```

如果你确实需要在主线程里继续用这个变量，就得自己 clone 一份：

```rust
let name_for_thread = name.clone();
let handle = thread::spawn(move || {
    println!("hello, {}", name_for_thread);
});
println!("main still has: {}", name);
handle.join().unwrap();
```

## 当变量需要在多个线程间共享

clone 能解决大部分问题，但有时候你希望改动能被所有线程看到——比如一个计数器。这时候只靠 move 就不够了，因为每个线程拿到的是独立的拷贝。

常见的做法是把共享状态放进 Arc，再配上内部可变性：

| 场景 | 推荐工具 |
|------|----------|
| 只读共享 | Arc\<T\> |
| 需要修改，且要同步 | Arc\<Mutex\<T\>\> |
| 只需要原子计数 | Arc\<AtomicUsize\> |
| 只是想等线程结束 | 不需要共享，直接 join |

一个计数器例子：

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..8 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            let mut num = counter.lock().unwrap();
            *num += 1;
        }));
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("result: {}", *counter.lock().unwrap()); // result: 8
}
```

注意循环里的写法：先在循环体内 Arc::clone，再 move 进闭包。如果直接 move 外面那个 counter，第一次迭代就会把它移走，循环后续就没得用了。

## 一个"看起来能借用"的例外

说了这么多"不能借用"，其实标准库里有一个特例：std::thread::scope。它允许你启动借用局部变量的线程，因为在 scope 结束前，主线程会等待所有派生线程结束：

```rust
use std::thread;

fn main() {
    let name = String::from("Rust");

    thread::scope(|s| {
        s.spawn(|| {
            println!("hello, {}", name); // 这次可以借用，不需要 move
        });
        // scope 结束前，这里派生的线程都会 join
    });

    // 此时线程已经结束，name 可以安全地被销毁
}
```

scope 的工作原理是：它借用了外部变量的作用域，并保证在返回前所有线程都结束。这样编译器就能证明，线程里哪怕持有 `&name`，也不会活过 name 的生命周期。代价是这些线程不能脱离 scope 存活——你没法把 JoinHandle 传出去再让它在别处 join。需要"发射后不管"的后台任务时，还是得回到 spawn + 'static + move 那条路上。

## 小结

下次再看到 closure may outlive the current function，可以按这个顺序排查：

1. 闭包里有没有借用局部变量？有就先考虑加 move。
2. move 之后变量在别处还要用？clone 一份单独给线程。
3. 多个线程要改同一份数据？用 Arc\<Mutex\<T\>\> 或 Arc\<AtomicUsize\>。
4. 其实只是想并行跑一段、然后等结果？thread::scope 能让你安全地借用。

记住核心那条：'static 要求的是"不依赖短命引用"，而不是"活到程序结束"。理解了这一点，编译器的报错就不再是障碍，而是一份关于内存安全的免费审查报告。
