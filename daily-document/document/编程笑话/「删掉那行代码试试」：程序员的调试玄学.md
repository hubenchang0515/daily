# 「删掉那行代码试试」：程序员的调试玄学

几乎每个程序员都说过这句话——"我先把这行删了试试"，然后 bug 真的消失了。它于是成了团队里最接近咒语的一句玩笑，和"重启一下""你清缓存了吗"并称为三大万能解法。本文从这句玩笑出发，聊聊它背后真正的调试方法：控制变量、二分定位、最小复现，以及为什么有些看着多余的代码其实一直在负重。

## 一句玩笑话，其实就是控制变量法

典型场景大概长这样：

```go
// 不知道谁加的，删了反而好了
time.Sleep(10 * time.Millisecond)
```

你删掉它，测试绿了；加回去，又红了。于是有人得出结论：这行代码有毒。

冷静一点看，你刚才做的事叫**控制变量**：一次只改动一处，观察结果是否变化。这是所有调试方法的地基，只不过大多数人把它做成了随机删改，而不是系统性的二分。区别在于：前者靠运气，后者能在有限步内收敛。

所以"删掉试试"本身没错，错在删完之后没有回答那个关键问题——**为什么删掉它就好了？**

## 删一行真的有用，通常逃不出这几种原因

| 被删掉的那行长啥样 | 真实原因 | 该顺着查的地方 |
| --- | --- | --- |
| `cache.clear()`、`localStorage.clear()` | 共享状态被无意清空或污染 | 全局单例、模块级变量 |
| `time.sleep(...)`、`Sleep(...)` | 它改变了时序，掩盖了竞态 | 锁、条件变量、初始化顺序 |
| `console.log(...)`、`print(...)` | 副作用触发了 getter 或惰性求值 | 代理对象、懒加载、属性描述符 |
| `random.seed(42)` | 固定了随机性，别处反而依赖随机 | 测试隔离与全局状态 |
| `os.environ[...] = ...` | 进程级环境被改写 | 环境变量、工作目录 |
| 一行看起来没用的 `import` | 导入时执行了注册逻辑 | 模块顶层代码 |

一个很常见的例子是 Python 的可变默认参数：

```python
def add(tag, bucket=[]):   # 改成 bucket=None 就"好了"
    bucket.append(tag)
    return bucket
```

单独跑测试永远通过，一跑全量就串味——因为 `bucket` 是函数对象上的一个共享列表，跨测试用例活着。删掉那行当然"好了"，但真正的修复是换掉默认值，再给这个行为补一条回归测试。

## 正经做法一：让机器帮你删

如果坏掉的版本很多，手动删是低效的。用 `git bisect` 让 Git 在提交历史里做二分：

```bash
git bisect start
git bisect bad                 # 当前版本有问题
git bisect good v1.2.0         # 这个版本是好的
git bisect run ./scripts/repro.sh
git bisect reset
```

`repro.sh` 只需要用退出码说话，0 代表好，非 0 代表坏：

```bash
#!/usr/bin/env bash
set -e
npm test -- --runInBand >/dev/null 2>&1
```

前提是复现得稳定。如果某些提交时好时坏，用 `git bisect skip` 跳过它们，别让一个 flaky 测试把二分带偏。合并提交很多时还可以加 `--first-parent`，只沿主线找。

## 正经做法二：把复现缩到最小

二分历史是找"哪次引入的"，缩小复现是找"哪几行导致的"。顺序很重要：先开个分支或存个现场，别在唯一的工作区里狂删。

```bash
git switch -c debug/minimize
# 或者更轻一点
git stash push -m "删代码前的现场"
```

然后重复一个朴素动作：删掉一半，问题还在就留这一半继续删；问题没了就换另一半。目标是得到一个能独立运行的二三十行脚本。到这一步，罪魁祸首往往自己就浮出来了。

如果复现输入是个巨大的文件，别手动删。C/C++ 场景可以直接交给工具：

```bash
creduce ./test.sh huge_input.c          # 缩小触发编译器/工具链问题的源文件
rr record ./my_program                  # Linux 上录制执行过程
rr replay                              # 之后可以反复确定性回放
```

`creduce` 会不断删除无关片段并验证问题仍存在，本质就是把"删掉试试"自动化了一千遍。

## 当"多余"的代码其实在负重

最有意思的是反方向：那行代码看着无用，删掉之后程序直接崩了。

```go
import _ "github.com/lib/pq" // 看着没用？删掉试试
```

删掉它，`sql.Open("postgres", ...)` 会提示 `unknown driver`。这个空白导入的唯一作用就是执行包级初始化，把驱动注册进去。类似的还有：

- 一次"多余的"读取，触发了 mmap 预取或缓存预热；
- 一个空实现，满足了接口，删掉后走进了另一条 fallback 分支；
- 一行 `volatile` 或内存屏障，看似不改变逻辑，却保证了可见性；
- 一个 `Sleep`，确实掩盖了竞态——它不是修复，但它是线索：删掉之后暴露出来的崩溃，才是真正要解决的事。

所以删代码之前先问一句：它是不是在承担某种**没有被写下来的契约**？如果答案是"不知道"，那就说明缺的不是删除的勇气，而是文档和测试。

## 让玄学变成可交接的知识

"删了就好了"最大的危害不是 bug，而是它把知识锁在了某个人的记忆里。三件事能把它变成团队资产：

1. **提交信息写原因，不写结论。** `fix` 和 `fix again` 之间差的不是字数，是信息量。用 `git log -S` 把那一行捞出来看看它当年的来路：

   ```bash
   git log -S 'time.Sleep' --oneline -- internal/worker.go
   ```

2. **给"为什么不能删"写一条回归测试。** 测试失败时的信息就是最好的注释。

3. **注释里写清现象和条件，而不是复述代码：**

   ```js
   // 不要删除：删掉后 Safari 上偶发表单提交丢失（#412）
   // 它让 DOM 更新在 focus 事件之前完成，等价于一次显式同步
   await nextTick()
   ```

下次再有人说"我删了一行就好了"，别急着鼓掌，也别急着合并。问一句"为什么"，然后把它写进提交、测试和注释里。玩笑留在群里就好，代码里只留证据。
