# 表达式里的求值顺序：同一行代码，换个编译器结果就变了

上周帮同事排查一个诡异的日志问题：同一段代码，在他的 macOS 上打印 `0 1`，部署到线上 Ubuntu 却变成 `1 0`。两人对着屏幕盯了十分钟，最后发现既不是编译器版本的锅，也不是标准库的 bug，而是这行代码本身就是未定义行为（UB）：

```cpp
#include <iostream>

int main() {
    int i = 0;
    std::cout << i++ << ' ' << i++ << '\n';
}
```

这类代码在面试和老项目里都特别常见。它看起来"能跑"，换台机器却悄悄换了语义。今天就把求值顺序这件事彻底理清楚。

## 先序关系：标准到底规定了什么

在 C++11 之前，标准用**顺序点（sequence point）**描述求值先后；C++11 之后换成了更精确的 **sequenced before（先序）**关系。核心规则可以浓缩成一句话：

> 如果两个对同一个标量对象的访问之间没有明确的先后关系，且其中至少有一个在修改它，那就是未定义行为。

这里的关键词是"没有明确先后"，标准称之为 **unsequenced（未排序）**。注意，UB 不是"结果不确定"这么温和——它意味着编译器可以对这段代码做任何事，包括删掉它、折叠成常数、或者返回一个你完全想不到的值。

## 几个经典翻车现场

下面几行代码，几乎每一个 C++ 程序员都写过或见过：

```cpp
int i = 0;

i = i++ + 1;        // 老标准里是 UB
int a[2] = {};
a[i] = i++;         // 老标准里是 UB
std::printf("%d %d\n", i++, i++);  // 函数参数，老标准里是 UB

i++ + ++i;          // 到今天仍然是 UB
```

很多人以为 `i++` 是"先取值再自增"，所以觉得 `i++ + ++i` 应该是 `0 + 2 = 2`。但标准只保证了单个 `i++` 内部的行为，并没有规定两次 `i++` 之间的先后。编译器完全可以先执行两次自增，再拿最终的 `i` 去相加，也可以交织执行。在 `-O2` 下，GCC 和 Clang 给出的结果可能不同，甚至同一编译器不同版本都不一样。

函数参数也是重灾区。`show(i++, i++)` 里，两个参数的求值在 C++14 及以前是 unsequenced，属于标准意义上的 UB；别指望"从左到右"或"从右到左"这种直觉。

## C++17 改了什么

C++17 对一批常见表达式补上了顺序保证，这也是很多人发现"升级标准后代码突然对了"的原因：

| 写法 | C++14 及更早 | C++17 起 | 建议 |
|------|-------------|----------|------|
| `i++ + ++i` | UB | **仍是 UB** | 永远别写 |
| `f(i++, i++)` | UB | 未指定顺序（不再是 UB） | 别写 |
| `std::cout << i++ << i++` | UB | 左到右，良定义，输出 `01` | 能写，但不推荐 |
| `i = i++ + 1` | UB | 良定义，`i` 变成旧值 + 1 | 能写，但别依赖 |
| `a[i] = i++` | UB | 良定义，先算右侧 | 能写，但别依赖 |

变化最大的是赋值和流插入：C++17 明确规定赋值表达式 `E1 = E2` 中 **E2 先于 E1 求值**；重载运算符也遵循内建运算符的顺序规则，于是 `std::cout <<` 终于保证了从左到右。

但请注意两点：第一，`+`、`-`、`*` 这些算术运算符的操作数**至今仍然是 unsequenced**，所以 `i++ + ++i` 没有任何"新标准救了你"的说法；第二，"不再是 UB"不等于"有了固定顺序"，`f(i++, i++)` 只是从 UB 降级成了 unspecified，你依然不该写。

## 为什么编译器不直接报错

理想情况下，编译器应该在编译期指出所有 UB。现实是，C++ 的语法允许太多合法但危险的组合，编译器只能尽力提醒。打开警告是第一步：

```bash
# GCC：-Wsequence-point 通常已随 -Wall 启用
g++ -std=c++14 -Wall -Wextra -O2 seq.cpp -o seq

# Clang：对应 -Wunsequenced，同样在 -Wall 里
clang++ -std=c++14 -Wall -Wextra seq.cpp -o seq
```

对前面那段 `std::cout << i++ << i++`，你会看到类似这样的提示：

```
warning: operation on 'i' may be undefined [-Wsequence-point]
warning: multiple unsequenced modifications to 'i' [-Wunsequenced]
```

至于 UBSan（`-fsanitize=undefined`），它对整数溢出、越界、未对齐访问很有效，但**抓不住未排序副作用**这类 UB——这点是很多人踩过的坑，别指望它兜底。

## 写出不依赖运气的表达式

规则其实很简单：**一个表达式里，对同一个对象最多修改一次，且修改时不要再读它。** 拿不准就拆行，用临时变量把顺序钉死：

```cpp
#include <iostream>

void show(int a, int b) {
    std::cout << "a=" << a << ", b=" << b << '\n';
}

int main() {
    int i = 0;

    // 危险：show(i++, i++);
    int first  = i++;   // first = 0, i = 1
    int second = i++;   // second = 1, i = 2
    show(first, second);

    // 危险：a[i] = i++;
    int a[3] = {};
    int idx = i++;      // idx = 2, i = 3
    a[idx] = 42;
    std::cout << "a[2]=" << a[2] << ", i=" << i << '\n';
}
```

编译运行，结果在任何编译器、任何优化级别下都一致：

```bash
g++ -std=c++17 -Wall -Wextra -O2 safe.cpp -o safe && ./safe
# a=0, b=1
# a[2]=42, i=3
```

另外记住少数几个**有明确保证**的运算符：`&&`、`||`、逗号 `,`、条件运算符 `?:` 都规定了严格的求值顺序（前两个还带短路）；赋值和流插入从 C++17 起也有了保证。除此之外，默认所有操作数都是"谁先谁后不确定"。

## 小结

求值顺序的问题之所以难查，是因为它不会崩溃、不会报错，只会安静地给出另一个答案。三个习惯能帮你远离它：

1. 看到 `i++`、`++i`、`i += 1` 出现在复杂表达式里，先警惕起来；
2. 不确定顺序时，拆成多条语句，用命名清楚的临时变量承接中间值；
3. 把 `-Wall -Wextra` 常开，看到 `-Wsequence-point` / `-Wunsequenced` 警告就立刻改，不要"先这样，回头再说"。

代码的可读性红利是双向的：你写清楚每一步的顺序，编译器和下一个读代码的人（很可能就是三个月后的你）都不用猜。
