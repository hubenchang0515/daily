# 循环变量只有一个：读懂 Go 的 for range

很多人第一次写并发代码，都会撞上同一个“灵异现象”：循环里启动了几个 goroutine，每个都打印自己的下标，屏幕上却齐刷刷全是最后一个数字。代码看起来毫无破绽，问题出在你对“循环变量”的假设上。Go 在很长一段时间里让每次迭代复用同一个变量；Go 1.22 改变了这一点，但改变是否生效，取决于一个很容易被忽略的开关——`go.mod` 里的版本号。本文把这三层串起来：变量为什么会被复用、闭包为什么抓住它，以及新旧语义下怎么写才不出错。

## 先把现象复现出来

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 5; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            fmt.Print(i, " ")
        }()
    }
    wg.Wait()
    fmt.Println()
}
```

在旧语义下，输出几乎总是：

```text
5 5 5 5 5
```

不是 goroutine 调度乱了，也不是 `i` 被写坏了。整个循环里只有一个 `i`，它的地址从第一次迭代到最后一次都不变。循环跑完时 `i == 5`，而 goroutine 往往在循环结束后才真正开始执行，于是它们读到的都是同一个、已经是 5 的变量。

同样的陷阱不只属于 goroutine。`defer` 也会把执行推迟到循环之后：

```go
for i := 0; i < 3; i++ {
    defer fmt.Print(i, " ")
}
```

旧语义输出 `3 3 3`；新语义输出 `2 1 0`。`range` 里的取值变量也不例外：

```go
names := []string{"alice", "bob", "carol"}
for _, name := range names {
    go func() {
        fmt.Println("hello", name)
    }()
}
```

旧语义下，三行很可能都打印 `hello carol`。

## 闭包抓走的是变量，不是当时的值

关键在于匿名函数捕获的是**变量本身**，而不是调用那一刻的值。`go func(){...}()` 和 `defer func(){...}()` 都没有参数列表，函数体里的 `i` 指向外层那个唯一的变量。等它们真正运行时，再去读这个变量的当前值，自然就是循环结束后的终值。

可以拿地址验证这一点：

```go
for i := 0; i < 3; i++ {
    fmt.Printf("%p\n", &i)
}
```

旧语义下三行地址完全相同；新语义下则是三个不同的地址。这个实验比看输出更直观，也更容易在排查时说服自己。

## 三种写法，哪种最稳

修复思路都是“让每个闭包拿到属于自己的那份值”。

**方式一：把值作为参数传进去。** 这是最稳的写法，不依赖任何语言版本：

```go
for i := 0; i < 5; i++ {
    wg.Add(1)
    go func(i int) {
        defer wg.Done()
        fmt.Print(i, " ")
    }(i)
}
```

参数在调用时求值并复制，函数体里的 `i` 是形参，和外层的循环变量彻底解耦。

**方式二：在循环体内做一次局部复制。**

```go
for i := 0; i < 5; i++ {
    i := i // 这一轮专属的副本
    wg.Add(1)
    go func() {
        defer wg.Done()
        fmt.Print(i, " ")
    }()
}
```

那个看起来有点奇怪的 `i := i`，在旧语义里是标准解法：右侧取旧变量的值，左侧用 `:=` 声明一个同名的、作用域仅限本轮迭代的新变量。

**方式三：让语言替你做这件事。** Go 1.22 起，循环头部用 `:=` 声明的变量在每次迭代都会新建，旧代码不用改就能得到正确结果。

| 写法 | `go.mod` ≤ 1.21 | `go.mod` ≥ 1.22 |
| --- | --- | --- |
| 直接捕获 `i` | 全是最后一个值 | 各自的值 |
| `func(i int){...}(i)` 传参 | 各自的值 | 各自的值 |
| `i := i` 后再捕获 | 各自的值 | 各自的值 |
| 循环外 `var i`，`for i = ...` | 共享，全一样 | 仍然共享 |

## Go 1.22 改了语义，但有个开关

新语义不是“装上 Go 1.22 就自动生效”，而是由每个模块自己的 `go.mod` 决定：

```text
module example.com/loopvar

go 1.22
```

`go` 指令低于 1.22，即使你用 Go 1.22 甚至更高版本的工具链编译，该模块内的循环仍然按旧语义处理——这是为了兼容存量代码而刻意保留的行为。反过来，工具链本身低于 1.22 时，无论 `go.mod` 写什么，都只能按旧语义走。

这一点在写库时尤其重要：语义跟着**代码所属模块的 go 指令**走，而不是跟着最终二进制的构建环境走。主模块声明 `go 1.22`、依赖库声明 `go 1.21`，库里的闭包依旧捕获共享变量。别指望升级调用方的 Go 版本能替依赖“顺手修好”。

升级后还有一个容易误读的信号：`go vet` 的 `loopclosure` 检查在新语义下不再对这些捕获报警。这不是项目突然变安全了，只是检查器知道变量不再共享。老项目如果还声明着 `go 1.21`，告警消失只能说明别的原因，值得回头确认一下 `go.mod`。

## 仍然会咬人的边界

新语义只作用于**循环头部用 `:=` 声明的变量**。如果变量在循环外声明，再用赋值符号推进循环，它始终只有一个：

```go
var i int
for i = 0; i < 3; i++ { // i 不是本轮新建的
    go func() { fmt.Print(i, " ") }()
}
```

`range` 中也一样：`for k, v := range m` 的 `k`、`v` 在新语义下每轮新建，但写成 `for k, v = range m` 时，捕获的仍是外部那两个变量。

另一个常见误解是顺带把 `range` 的取值变量当成原元素的引用。无论哪个语义版本，`v` 都是元素副本：

```go
nums := []int{1, 2, 3}
for _, v := range nums {
    v *= 10 // 改的是副本，nums 没变
}
fmt.Println(nums) // [1 2 3]
```

要修改元素，得用索引 `nums[i] = ...`，这和循环变量是否共享是两件事。

## 排查与预防

遇到“结果全一样”，按这个顺序看：先 `head -n 5 go.mod` 确认 `go` 指令，再 `go version` 确认工具链，然后检查闭包里引用的是不是循环头部声明的变量。

写新项目时，把 `go.mod` 升到 1.22 以上并享受新语义，代价是要清楚它会影响所有循环；维护老项目时，不必为了修一个 bug 去动模块版本，**传参写法**在任何版本下都正确，也不会让读代码的人怀疑是不是漏看了 Go 版本。

把“循环变量只有一个”这句话记在心里。下次看到闭包、goroutine、`defer` 和循环变量同框出现，先问一句：这个变量是每轮一个新的，还是从头到尾只有一个？答案通常就藏在 `go.mod` 的那行版本号里。
