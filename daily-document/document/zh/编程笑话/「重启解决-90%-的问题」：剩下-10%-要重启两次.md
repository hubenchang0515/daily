# 「重启解决 90% 的问题」：剩下 10% 要重启两次

在程序员的工具箱里，最趁手的从来不是调试器，也不是那个装了三十个插件的 IDE，而是一句朴素的「你重启一下试试」。它跨语言、跨框架、跨操作系统，甚至跨物种——打印机卡纸的时候，这句话同样适用。

更奇妙的是，它经常真的有用。于是我们不得不面对一个尴尬的事实：这句听起来像敷衍的话，背后其实藏着一整套关于状态的知识。重启不是玄学，它是一次大规模的状态清零；而所谓「剩下 10% 要重启两次」，通常是因为第一次只重启了应用，第二次才想起来浏览器还开着。

## 一、重启到底重启了什么

一次重启，清掉的东西远比我们以为的多：

- **进程内存里的旧代码**：热更新失效、模块缓存、单例里缓存的配置。
- **环境变量和命令行参数**：你改了 `.env`，但进程还攥着启动那一刻的值。
- **网络连接池**：数据库主从切换后，池子里全是连向旧主库的坏连接。
- **DNS 与 hosts 缓存**：改了 `/etc/hosts`，浏览器和 `systemd-resolved` 还记得旧 IP。
- **文件描述符与锁文件**：泄漏的 fd、没删掉的 `pid` 文件、占着的临时文件。
- **前端的构建产物与 Service Worker**：你部署了新版本，用户拿到的还是旧_resource_。

想验证「是不是环境变量没更新」，不用猜，直接看进程手里的那份：

```bash
# /proc/<pid>/environ 用 NUL 分隔，转成行再筛
tr '\0' '\n' < /proc/12345/environ | grep API_URL
```

想确认「是不是旧文件还被占着」：

```bash
ls -l /proc/12345/fd | grep deleted
```

这两条命令经常能把一个「明明改了却没生效」的灵异事件，还原成一次普普通通的状态遗忘。

## 二、重启的三个段位

| 段位 | 命令 | 清掉了什么 | 代价 |
| --- | --- | --- | --- |
| 应用级 | `systemctl restart myapp` | 进程内存、配置、连接池 | 秒级不可用 |
| 容器级 | `docker restart myapp` | 容器内一切，挂载卷除外 | 同上，但更彻底 |
| 机器级 | `sudo reboot` | 内核、网络栈、所有缓存 | 全场重来，群里要发通知 |

民间还流传着两个隐藏段位：**第四段位**是「重启同事的机器」——技术难度为零，社交难度极高；**第五段位**是「重启自己」——离开屏幕睡一觉，第二天醒来 bug 还在，但你看它的眼神变了。

有人把重启做成了一个频率问题：一天重启一次叫「日常维护」，一小时重启一次叫「稳定性建设」，一分钟重启一次叫「我们在做弹性伸缩」。话术决定命运。

## 三、为什么有些 bug 重启后才消失

最常见的原因是：**配置只在启动时读一次**。

```python
# app.py
import config          # 第一次导入后，config.py 就被放进 sys.modules 了
print(config.TIMEOUT)  # 之后你改 config.py，这里永远打印旧值
```

除非显式重载，否则模块缓存会一直护着那份旧配置：

```python
import importlib, config
importlib.reload(config)
```

Node 世界同理：

```js
delete require.cache[require.resolve('./config')];
const config = require('./config'); // 这次才是新的
```

再比如前端的 Service Worker：它像个忠实但固执的管家，把旧 HTML 和旧 JS 锁在缓存里。你发版了，用户刷新十次，管家十次都递上同一份旧文件。这时候「重启两次」里的第二次，往往就是关掉浏览器再打开——或者干脆 `unregister()` 那个管家。

还有一类更隐蔽：后台线程或定时器拿着旧闭包。进程没重启，那个每天凌晨两点执行的任务，用的还是三年前那套参数。

## 四、重启把证据也一起冲走了

重启是很好的恢复手段，却是糟糕的定位手段。一次 `restart`，可能同时送走了：

- 还没落盘的堆栈和堆转储；
- 内存里那份「现场」，包括触发问题的请求上下文；
- 缓冲区的最后几百行日志；
- 最难得的复现路径。

线上出问题，第一反应就是重启，重启后一切正常，于是问题被记为「已恢复，原因待查」。三周后它再来一次，你还是那句「重启一下试试」——这就是玄学诞生的全过程。

所以重启之前，先花三十秒留证据：

```bash
# Java：线程栈和堆
jstack -l 12345 > /tmp/jstack.txt
jmap -dump:format=b,file=/tmp/heap.hprof 12345

# Go：协程现场（需暴露 pprof）
curl -s 'http://localhost:6060/debug/pprof/goroutine?debug=2' \
  > /tmp/goroutine.txt
```

留完再重启，你至少还有机会在事后当一次侦探，而不是永远当那个只会按开关的人。

## 五、重启前 60 秒检查清单

下次手要伸向 `restart` 之前，先过一遍：

1. `git diff`——确认你以为没改的东西到底改没改。
2. `ps -o lstart=,cmd= -p <pid>`——看进程是什么时候启动的，拿着什么参数。
3. `tr '\0' '\n' < /proc/<pid>/environ | grep KEY`——看环境变量是不是旧的。
4. `ls -l /proc/<pid>/fd | grep deleted`——看有没有已删除但仍被占着的文件。
5. 看一眼日志末尾：`journalctl -u myapp -n 100 --no-pager`。
6. 确认你改的配置和进程读的配置，是同一份。
7. 确认前端缓存已经失效，别让用户替你缓存旧版本。

这七步做完，一半情况下你会找到比重启更精准的办法；另一半情况下你仍然会重启，但至少知道自己在清什么。

## 结语

重启之所以像万能药，是因为它把一整天的状态债一次性还清了。可债主没消失，只是换了身衣服——下次还会来敲门。

所以真正的规矩不是「别重启」，而是重启之前多问一句：**为什么重启就好了？** 这句话的答案，往往才是那个真正的 bug。至于那 10% 要重启两次的情况——第一次重启机器，第二次重启那个坚持「我明明改了」的自己。
