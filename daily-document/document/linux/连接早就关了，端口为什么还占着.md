# 连接早就关了，端口为什么还占着

服务重启时抛出 `Address already in use`，`ss` 一查，端口上挂着一串 TIME_WAIT，可连接明明已经结束了。这篇文章从四次挥手讲起，说清 TIME_WAIT 为什么会存在、什么时候它才是真故障，以及哪些内核参数可以调、哪些碰不得。

## 现象：端口被自己占住

最常见的现场是这样的：改完配置重启服务，启动脚本失败，日志里只有一句 `bind: Address already in use`。用 `ss` 看一眼，发现 8080 端口上全是这种记录：

```bash
$ ss -tan state time-wait | head
TIME-WAIT  0      0      127.0.0.1:8080    127.0.0.1:52344
TIME-WAIT  0      0      127.0.0.1:8080    127.0.0.1:52345
TIME-WAIT  0      0      127.0.0.1:8080    127.0.0.1:52346
```

第一反应是"有进程没退干净"，于是 `lsof -i:8080`、`ss -tanp` 轮番上，结果什么都查不到。这不是工具失灵：TIME_WAIT 是内核里的一条状态记录，没有对应的文件描述符，也没有所属进程，杀谁都没用。它只会自己等时间到了消失。

## 四次挥手之后，谁进 TIME_WAIT

TCP 关闭连接需要四个包。假设客户端主动关闭：

1. 客户端发 FIN，进入 FIN_WAIT_1；
2. 服务端回 ACK，客户端进入 FIN_WAIT_2；
3. 服务端发完数据后也发 FIN，客户端进入 TIME_WAIT；
4. 客户端回最后一个 ACK，等一段时间后才彻底关闭。

关键在第四步：**先关的一方进 TIME_WAIT**。谁先发 FIN，谁等。所以短连接场景下，可能是服务端主动关（Web 服务器常见），也可能是客户端主动关，取决于应用和协议实现。判断方法是看 `ss` 输出里本地地址和远端地址谁固定在监听端口上。

等待时长理论上是 2×MSL（报文最大生存时间），Linux 里直接写死为 60 秒，内核宏叫 `TCP_TIMEWAIT_LEN`，不重新编译内核改不了。网上"把 TIME_WAIT 调到 5 秒"的说法基本是误导。

## 这两个等待不是浪费

TIME_WAIT 承担了两件事，理解了它们就不敢随便关了。

**第一，保证最后的 ACK 能送到。** 如果第四个 ACK 丢了，服务端会重发 FIN。此时客户端如果已经彻底关闭，只能回一个 RST，服务端那边就会看到连接异常终止。留在 TIME_WAIT 里，还能正常重发 ACK。

**第二，让旧连接的残留报文在网络里消散。** 同一个四元组（源 IP、源端口、目的 IP、目的端口）如果立刻被新连接复用，网络里迟到的旧数据包可能混进新连接，被当成合法数据。等 2×MSL 是为了让这些孤儿报文自然死亡。

所以 TIME_WAIT 本身是保护机制，不是 bug。真正需要处理的只有两种情况：监听端口 bind 失败，以及客户端端口耗尽。

## 服务端 bind 失败：缺的是 SO_REUSEADDR

服务端的监听 socket 是 `*:8080`，而 TIME_WAIT 记录是 `127.0.0.1:8080 ↔ 客户端IP:端口`，四元组并不相同。按理说可以同时存在，但内核默认禁止新 socket bind 到仍被占用端口，于是启动失败。

正确的做法是在创建监听 socket 时设置 `SO_REUSEADDR`：

```python
import socket

s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(("0.0.0.0", 8080))
s.listen()
```

主流 Web 服务器和框架都已经默认打开了这个选项，所以正常情况下重启服务并不会失败。如果自己写的服务总在这里卡住，先检查这一行。它只影响 bind 行为，不会让旧连接的数据串到新连接里，可以放心用。

## 客户端端口耗尽：错误其实是 Cannot assign requested address

另一种场景是压测或爬虫脚本跑着跑着突然连不上了，报 `connect: Cannot assign requested address`。这跟服务端没关系：客户端每发一次短连接，就会占掉一个临时端口进入 TIME_WAIT，一分钟内几千次请求就能把默认范围耗光。

```bash
# 看临时端口范围，默认通常是 32768 60999
sysctl net.ipv4.ip_local_port_range

# 统计当前 TIME_WAIT 数量
ss -tan state time-wait | wc -l
```

按默认范围算，大约 2.8 万个可用端口，每分钟几千连接确实撑不住。这时有几个层次的解法：

- **优先改应用**：用长连接或连接池，别为每个请求新建 TCP 连接。这是根本解法。
- **扩大端口范围**：`sysctl -w net.ipv4.ip_local_port_range="1024 65535"`，简单直接，只是把天花板抬高一些。
- **开启时间戳与复用**：确认 `net.ipv4.tcp_timestamps=1` 后设置 `net.ipv4.tcp_tw_reuse=1`，允许内核在满足安全条件时复用 TIME_WAIT 中的出方向连接。它只对主动发起连接的一侧有效，对监听端口没用。

要持久生效，把参数写进 `/etc/sysctl.d/` 下的配置文件，别直接改 `/proc`。

## 几个流传很广的坑

| 参数 / 说法 | 实际情况 |
| --- | --- |
| `tcp_fin_timeout` | 控制 FIN_WAIT_2 的超时，跟 TIME_WAIT 时长无关，调它没用 |
| `tcp_tw_recycle` | Linux 4.12 起已移除，且会在 NAT 环境下误丢连接，别再照抄老教程 |
| `net.ipv4.tcp_tw_reuse=0` | 只影响出方向复用，不会让已有 TIME_WAIT 消失 |
| "用 kill 清掉 TIME_WAIT" | 没有进程可杀，只能等超时或用上面几条路 |

还有个容易混淆的点：`ss` 里的 `-p` 看不到 TIME_WAIT 的进程信息，是正常的；但 `ESTABLISHED` 和 `FIN_WAIT` 阶段通常能看到。看不到进程就以为是"幽灵连接"，是排查时最常见的误判。

## 小结

遇到 TIME_WAIT，先别急着动内核参数。问自己三个问题：是谁主动关闭的？现在是 bind 失败还是连不出去？数量是否在短时间内异常暴涨？

- bind 失败 → 检查 `SO_REUSEADDR`；
- 连不出去 → 应用改长连接，再考虑扩端口范围和 `tcp_tw_reuse`；
- 数量暴涨但没有报错 → 多半是上游把长连接改成了短连接，去查调用方。

TIME_WAIT 是 TCP 最后一道保险。它占着的不是资源浪费，而是你和网络之间的一份契约。弄清它为什么在，比想办法让它消失更重要。
