# 删掉的大文件，空间为什么没回来

你在服务器上发现磁盘快满了，于是 `rm` 掉了一个几十 GB 的日志文件。命令顺利执行，`ls` 也看不到它了，但 `df -h` 显示的可用空间几乎没变。文件明明“没了”，空间却像被什么东西悄悄占着。

这类问题很常见，根源通常不是 `rm` 失效，而是：**文件名被删了，但文件数据还被某个进程占用着**。只要还有进程打开着它，内核就不会真正释放磁盘块。

## 先分清两件事：`df` 和 `du` 在看什么

排查时先把现象看准，避免在错误方向上打转。

| 命令 | 统计对象 | 常见用途 |
| --- | --- | --- |
| `df -h` | 文件系统层面的已用/可用空间 | 看某个分区还剩多少空间 |
| `du -sh /path` | 目录树中“能被遍历到”的文件大小总和 | 找哪个目录占空间大 |

如果出现下面这种组合，基本可以怀疑“已删除但仍被打开”的文件：

- `df -h` 显示分区很满
- `du -sh /var`（或对应目录）加起来明显小于 `df` 的已用量
- 你刚删过一个大文件，但空间没回升

原因在于：`du` 只能统计目录中还存在的路径；而 `df` 统计的是文件系统上已分配的数据块。一个文件即使从目录中消失，只要还有打开的文件描述符指向它，这些数据块就仍然算作“已使用”。

## 文件为什么删了还占空间

在 Linux 中，目录项（文件名）和 inode（文件元数据与数据块引用）是分开的。可以粗略理解为：

- 文件名是“入口”
- inode 和数据块是“实际内容”

`rm` 删除的是目录项。当某个 inode 的链接数降为 0，且没有任何进程再打开它时，内核才会释放对应的数据块。只要还有进程持有打开的文件描述符，空间就会一直被占用，直到进程关闭文件或退出。

这也是为什么日志文件特别容易中招：程序启动后一直打开日志写入，你在外面 `rm` 掉文件名，程序却浑然不觉，继续往那个“已经看不见”的文件里写。

## 动手复现：亲眼看看空间是怎么卡住的

下面用一个简单实验复现问题。建议在测试机或 `/tmp` 下操作。

```bash
# 1. 准备一个临时目录
mkdir -p /tmp/space-demo
cd /tmp/space-demo

# 2. 创建一个约 500MB 的文件
dd if=/dev/zero of=big.log bs=1M count=500 status=progress

# 3. 用 Python 打开文件并保持不退出（模拟服务进程持有日志文件）
python3 - <<'PY'
import time
f = open('big.log', 'a')
print('file is opened, pid =', __import__('os').getpid())
time.sleep(600)
PY
```

另开一个终端执行：

```bash
cd /tmp/space-demo

# 4. 删除文件名
rm big.log
ls -lh

# 5. 查看分区空间（不会立刻释放 500MB）
df -h /tmp

# 6. 找出“已删除但仍被打开”的文件
sudo lsof +L1 /tmp
```

你会看到类似输出（节选）：

```text
COMMAND   PID USER   FD   TYPE DEVICE SIZE/OFF NLINK NODE NAME
python3 12345 user    3w   REG  253,0 524288000     0  ... /tmp/space-demo/big.log (deleted)
```

关键信息有三个：

- `NAME` 末尾带 `(deleted)`：路径已被删除
- `NLINK` 为 `0`：已经没有目录项指向它
- `SIZE/OFF` 仍然很大：磁盘块还在

回到第一个终端按 `Ctrl+C` 结束 Python 进程，再看 `df -h /tmp`，空间才会真正释放。

## 排查线上问题：定位是谁占着文件

确认是“删后未释放”后，下一步是找出占用者。常用命令如下。

### 1. 直接列出已删除但打开的文件

```bash
# 查看整个系统
sudo lsof +L1

# 只看某个挂载点，范围更小、更快
sudo lsof +L1 /var
```

`+L1` 表示列出链接数小于 1 的文件，非常适合定位这类问题。重点看 `COMMAND`、`PID`、`SIZE/OFF` 和 `NAME`。

如果系统没有 `lsof`，也可以从 `/proc` 入手：

```bash
# 在所有进程的文件描述符中查找 deleted
sudo find /proc/*/fd -ls 2>/dev/null | grep '(deleted)'
```

或更有针对性地查看某个可疑进程：

```bash
ls -l /proc/<PID>/fd | grep deleted
```

### 2. 判断影响范围

找到大文件后，先确认两点：

- 这个文件属于哪个服务（`PID` 对应的进程名、启动参数、systemd 单元）
- 是否可以安全地重启该服务或让它重新打开日志

```bash
ps -fp <PID>
sudo systemctl status <service-name> --no-pager
```

不要一上来就杀进程，尤其是数据库、消息队列这类有状态服务，先评估影响。

## 怎么把空间立刻拿回来

处理方式取决于你能否中断对应进程。

### 方法一：重启或重载持有文件的进程（最稳妥）

这是最干净的做法。进程退出或关闭文件描述符后，内核会释放空间。

```bash
# 示例：重启某个服务
sudo systemctl restart your-service

# 或让支持重载的服务重新打开日志文件
sudo systemctl reload nginx
```

适合大多数“删了日志文件但空间没降”的场景。前提是该服务支持平滑重启/重载，或者你能接受短暂中断。

### 方法二：在线截断文件描述符（应急止血）

如果暂时不能重启进程，但磁盘已经告急，可以通过 `/proc/<PID>/fd/<FD>` 把文件内容截断为 0：

```bash
# 假设 lsof 查到 PID=12345, FD=3
sudo truncate -s 0 /proc/12345/fd/3
# 或者
sudo : > /proc/12345/fd/3
```

这样能立即释放空间，但有几个注意事项：

- **不会修复程序的写入位置**：有些程序仍按旧偏移量继续写，文件可能变成稀疏文件（逻辑大小很大，实际占用较小），表现会因程序而异。
- **日志内容会丢失**：截断后原内容不可恢复。
- **只是临时措施**：根因是日志没有正确轮转，之后仍应安排重启或修复日志策略。

对“日志把磁盘写满”的紧急情况，这个办法很实用；但处理完后务必跟进长期方案。

### 方法三：不要对已删除路径执行 `truncate`

很多人会尝试：

```bash
truncate -s 0 /var/log/app.log
```

如果这个路径已经被 `rm` 删除，上面的命令只会创建一个**新的同名空文件**，旧文件的数据块依然被原进程占用，空间不会释放。对已删除文件，必须针对 `/proc/<PID>/fd/<FD>` 或让进程重新打开文件。

## 如何避免下次再踩坑

与其事后救火，不如把日志和临时文件的生命周期管好。

- **用 logrotate 管理日志**：配置按大小或按天轮转，避免单个文件无限增长。
- **理解 `copytruncate` 的取舍**：它通过“复制后截断原文件”工作，不需要程序重开文件句柄，适合不支持 reopen 的程序；但在高并发写入时可能丢少量日志。
- **优先使用“重命名 + 通知程序重开”模式**：如 `delaycompress` 搭配 `postrotate` 发送信号，让程序重新打开新日志文件，更可靠。
- **清理前先确认是否被打开**：对怀疑的大文件，先 `lsof /path/to/file` 看看有没有进程在用。
- **给关键分区加监控与告警**：磁盘使用率、inode 使用率都要监控，提前发现比凌晨扩容从容得多。

一个简单的 logrotate 配置示例（按需调整路径和服务名）：

```conf
/var/log/myapp/*.log {
    daily
    rotate 7
    missingok
    notifempty
    compress
    delaycompress
    sharedscripts
    postrotate
        systemctl reload myapp >/dev/null 2>&1 || true
    endscript
}
```

## 小结

`rm` 只移除了文件名，不等于立刻回收磁盘空间。遇到“删了文件但 `df` 不降”，按这个顺序排查通常就够了：

1. 用 `df -h` 和 `du -sh` 对比，确认是文件系统占用与目录可见内容不一致。
2. 用 `sudo lsof +L1 /挂载点` 找出 `(deleted)` 且体积大的打开文件。
3. 优先重启或重载对应服务，安全地释放文件描述符。
4. 磁盘告急时，可临时 `truncate -s 0 /proc/<PID>/fd/<FD>` 止血，再补上日志轮转策略。

把“删除路径”和“释放空间”区分开，这类看似玄学的磁盘问题其实很好定位。
